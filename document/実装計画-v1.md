# 実装計画 v1

作成日: 2026-03-27

## 1. この文書の目的

この文書は、この会話時点で合意した MVP の実装内容を、漏れなく・後から見返しても解釈がぶれない粒度で固定するためのもの。

本書は次の方針で記述する。

- まず MVP で何を作るかを固定する
- あえて「MVP ではやらないこと」も明文化する
- 可能な限り一次情報で裏を取る
- 直感ではなく、ブラウザ制約・Cloudflare 制約・Google Maps 制約を前提に設計する

## 2. 今回の結論

MVP は以下の構成で進める。

- フロントエンド: React + TypeScript + Vite
- API 層: Hono + TypeScript
- デプロイ先: Cloudflare Workers を中心に構成する
- 実行形態: 1つの Cloudflare プロジェクトで静的アセット配信と API をまとめる
- 位置情報更新: クライアント主導
- 外部 API 呼び出し: Worker 経由
- PWA / オフライン / バックグラウンド / 再開機能: MVP 対象外

重要なのは、MVP は「数秒ごとの案内更新を行うブラウザ版の実験」であって、「ロック画面やバックグラウンドまで含む完成版ナビアプリ」ではない、という点である。

## 3. MVP で提供するユーザー価値

MVP のユーザー価値は 1 つに絞る。

- 現在地から、指定した片道時間で行ける場所を自動選定し、目的地名を UI 上では明かさず、テキストと矢印中心で案内する

MVP の成功条件は以下とする。

- スマホブラウザで位置情報が取得できる
- 出発地点確認ができる
- 希望時間と有料道路可否を入力できる
- サーバー側で候補地選定とルート検証ができる
- フロント側で現在位置に応じて次の案内文を更新できる
- 音声案内は「使えれば使う」が、使えなくても破綻しない

## 4. MVP のスコープ

### 4.1 含めるもの

- 位置情報権限の確認
- 現在地取得
- 出発地点の確認 UI
- 希望時間入力
- 有料道路可否入力
- サーバーでの候補地選定
- 候補地の Google Maps 側での解決
- ルート取得
- ルート所要時間の妥当性判定
- ステップ単位の案内表示
- 数秒ごとの案内再評価
- ルート逸脱の簡易検知
- 逸脱時の「元のルートに戻ってください」表示
- 可能なブラウザでは Screen Wake Lock
- Google Maps の attribution 表示
- 最低限のプライバシー表示

### 4.2 含めないもの

- PWA インストール導線
- Service Worker によるオフライン対応
- 画面再読み込み時の復元
- ログイン
- アカウント管理
- バックグラウンド動作
- ロック画面中の案内継続
- 逸脱時の自動再ルート検索
- 地図 UI
- SNS 共有
- 行き先予測ゲーム化

## 5. MVP の前提を一次情報で補正した結果

この会話では途中で `Cloudflare Pages + Workers` という案も出たが、公式ドキュメントを確認したうえで v1 では以下に補正する。

- 新規プロジェクトは Cloudflare Workers の Static Assets を第一候補とする
- Pages は必須ではない
- API と静的配信を同一プロジェクトにまとめ、CORS とデプロイ対象を減らす

理由は以下。

- MVP は「最小限で早く動くこと」が優先
- フロントと API を別サービスに分けると設定が増える
- Cloudflare 無料枠では Worker リクエスト数と CPU 制約を強く意識すべき
- 静的アセットは無料で配信できる一方、Functions / Workers 呼び出しは無料枠を消費する

補正点は Cloudflare だけではない。

- `watchPosition()` は「3秒ごとに必ず呼ばれる API」ではない
- `coords.heading` は常に頼れる前提にしてはいけない
- 目的地をブラウザに渡す以上、完全な秘匿はできない
- さくらの AI Engine は API 仕様上 OpenAI 互換のチャット補完を提供するが、利用可能モデルはコントロールパネル依存で固定名を前提にすべきではない
- `speechSynthesis.speak()` は user activation なしで失敗する実装がある
- Cloudflare Workers Free の CPU 制約は厳しいが、HTTP request の wall-clock duration 自体には hard limit がない
- Cloudflare の zone-level rate limiting は Free でも使えるが、Free の counting period は 10 秒単位に制約がある
- Google Routes は `Routes Preferred` と混同せず、通常の `Routes API v2` を固定採用したほうが実装の迷いが少ない

## 6. アーキテクチャ方針

### 6.1 物理構成

MVP の物理構成は以下。

```text
[Smartphone Browser]
  React + TypeScript + Vite
  - Geolocation
  - Navigation state machine
  - SpeechSynthesis (optional)
  - UI rendering
         |
         | HTTPS fetch
         v
[Cloudflare Worker]
  Hono
  - Request validation
  - LLM prompt assembly
  - Sakura AI Engine call
  - Google Places / Routes call
  - Response shaping
         |
         +--> Sakura AI Engine
         +--> Google Maps Platform
```

### 6.2 論理構成

コードは論理的に 3 層へ分ける。

- `frontend`: 画面・位置情報・案内更新
- `backend`: API 入口・外部 API 呼び出し・整合性判定
- `shared`: 型定義・純関数・共通スキーマ

ただしデプロイは 1 サービスに寄せる。

### 6.3 1 サービスにまとめる理由

- CORS を考えなくてよい
- API ベース URL の環境差分が減る
- デプロイミスが減る
- 公開 URL が 1 つで済む
- MVP の保守コストが低い

### 6.5 ディレクトリごとの責務

- `frontend`: ブラウザで動くものだけを置く
- `backend`: Worker ランタイムで動くものだけを置く
- `shared`: React と Worker のどちらにも依存しない型・定数・純関数だけを置く
- `tests`: 各 workspace に散らしすぎない統合テスト置き場
- `document`: 要件・設計・運用文書

### 6.6 依存方向のルール

依存方向は固定する。

- `frontend -> shared` は可
- `backend -> shared` は可
- `shared -> frontend` は不可
- `shared -> backend` は不可
- `backend -> frontend` は不可
- `frontend -> backend` のソース直接 import は不可

API 越しの依存だけを許す。

### 6.7 ルート設定ファイルの置き場所

モノレポだが、Cloudflare 向け設定は `backend/` に寄せる。

理由。

- 実際に deploy される Worker 本体は backend 側だから
- `wrangler.jsonc` の責務が明確になる
- `frontend/dist` を asset として backend 側から参照しやすい

### 6.8 既存ディレクトリ名の扱い

既存の `fronetend/` は typo であり、正式採用しない。

今後の正式名は必ず `frontend/` とする。

実装開始時には以下のどちらかを行う。

- `fronetend/` を削除して `frontend/` を新設する
- 既存内容がある場合のみ `frontend/` に移してから削除する

### 6.9 workspace と build の基本ルール

workspace は root の `package.json` で管理する。

- package manager はまず `npm workspaces` を採用する
- root では workspace 横断の script だけを定義する
- 各 workspace は自分の build/test 設定だけを持つ

build 順序は固定する。

1. `shared`
2. `frontend`
3. `backend`

deploy の考え方。

- `frontend` は `dist/` を出力する
- `backend` の `wrangler.jsonc` から `frontend/dist` を static assets として参照する
- 本番デプロイの入口は `backend` である

## 7. なぜこの言語・フレームワークなのか

### 7.1 React + TypeScript

採用理由。

- Geolocation / SpeechSynthesis / 画面状態管理がフロント中心である
- 型のある状態遷移を書きやすい
- ルート・案内・ API レスポンスの型をサーバーと共有しやすい
- Vite で最小構成を早く立ち上げやすい

### 7.2 Hono + TypeScript

採用理由。

- Worker ランタイムと相性が良い
- ルーティングが軽い
- TypeScript でフロントと API 契約を揃えやすい
- MVP で必要な責務は薄い API 層なので、重量級フレームワークは不要

### 7.3 Docker を MVP に入れない理由

現時点では Docker は採用しない。

- Cloudflare Worker の実行形態とローカル Docker の差が大きい
- MVP ではコンテナ運用の再現性より、実装速度のほうが重要
- ローカル開発は `npm` または `pnpm` と `wrangler` で十分

将来、別実行基盤へ移るときに再検討する。

## 8. MVP のユーザーフロー

1. ユーザーがトップ画面を開く
2. 位置情報利用の説明を表示する
3. 現在地取得を試みる
4. 現在地が取れたら、出発地点確認 UI を出す
5. ユーザーが希望時間と有料道路可否を入力する
6. フロントが `/api/navigation/start` を呼ぶ
7. Worker が候補地選定、場所解決、ルート取得、妥当性判定を行う
8. 問題なければ、フロントへナビゲーション開始用の最小データを返す
9. フロントが位置監視を開始する
10. 現在位置とルート step を見比べて案内文を更新する
11. 到着または中止で終了する

## 9. MVP の API 設計

MVP の本番 API はできるだけ少なくする。

### 9.0 外部 API 契約の固定

MVP では外部 API の契約を以下に固定する。

- Google Routes: `POST https://routes.googleapis.com/directions/v2:computeRoutes`
- Google Places Text Search (New): `POST https://places.googleapis.com/v1/places:searchText`
- Sakura AI Engine chat completions: `POST https://api.ai.sakura.ad.jp/v1/chat/completions`

採用しないもの。

- Google Routes Preferred
- Google Routes `v1alpha`
- 旧 Places Web Service 前提の設計

この固定は、実装時のエンドポイント揺れと課金/機能差の混乱を避けるためのもの。

### 9.1 必須 API

#### `POST /api/navigation/start`

責務。

- 入力値の検証
- LLM への問い合わせ
- 候補地の解決
- ルート取得
- 所要時間の整合性判定
- UI に返す最小データ生成

リクエスト案。

```json
{
  "origin": {
    "lat": 35.0,
    "lng": 139.0
  },
  "durationMinutes": 90,
  "tollRoadsAllowed": true
}
```

レスポンス案。

```json
{
  "status": "ok",
  "route": {
    "distanceMeters": 12345,
    "durationSeconds": 5400,
    "steps": []
  },
  "ui": {
    "initialInstruction": "800m先を右です",
    "showDestinationName": false
  }
}
```

`status` は少なくとも以下を持つ。

- `ok`
- `no_match`
- `validation_failed`
- `upstream_error`

#### `GET /api/health`

責務。

- デプロイ確認
- 監視の最小入口

### 9.2 `POST /api/navigation/start` の応答目標

これは暫定の SLO であり、実機検証後に調整する。

- 目標: P95 4 秒以内
- hard timeout: 8 秒
- 8 秒を超えたら `upstream_error` として失敗させる

理由。

- ナビ開始時に長く待たせると UX が急激に悪化する
- Workers の CPU ではなく、ユーザー待機時間と upstream 不安定性を制御したい

### 9.3 MVP では入れない API

- 再ルート検索 API
- 保存済み案内復元 API
- ユーザー履歴 API
- 音声ファイル生成 API

## 10. Worker 内部処理の詳細

`POST /api/navigation/start` の内部フローは以下。

1. 入力を検証する
2. 位置情報・希望時間・有料道路可否から、物理制約込みの LLM プロンプトを組み立てる
3. LLM に候補地を問い合わせる
4. `no_match` ならそこで終了する
5. 候補地テキストを Google 側で場所解決する
6. 解決できなければ、再試行方針に従って次候補または再プロンプトへ進む
7. 解決した place ID を使って Routes API を叩く
8. 所要時間が希望条件から大きく外れるなら不採用
9. 条件を満たした最初のルートを返す
10. UI に不要な目的地情報は落として返す

### 10.0 入力制約

公開 API として最低限の制約を入れる。

- `durationMinutes` は 30 以上 1800 以下
- 数値は有限値のみ許容
- `origin.lat` / `origin.lng` は緯度経度の範囲内のみ許容
- request body 上限は 2KB 程度に固定
- 文字列長に上限を設ける

目的は防御であり、柔軟性ではない。

### 10.0.1 外部依存の timeout / retry / backoff

MVP の初期値を以下に置く。

- Sakura AI Engine:
  - timeout: 3000ms
  - retry: 1 回
  - retry 対象: network error, timeout, HTTP 429, HTTP 5xx
- Google Places Text Search:
  - timeout: 1500ms
  - retry: 1 回
  - retry 対象: network error, timeout, HTTP 429, HTTP 5xx
- Google Routes:
  - timeout: 2000ms
  - retry: 0 回

backoff は単純指数ではなく、MVP では短い固定待ちで十分とする。

- 1 回目再試行前の待ち: 250ms

再試行しないもの。

- 入力不正
- Places の結果空配列
- Routes の成功レスポンスだが `routes[]` が空

理由。

- 無闇な再試行は公開 API ではコスト増になりやすい
- 「結果がない」ケースは transient failure ではない可能性が高い

### 10.1 LLM 出力形式

MVP では UI に見せる目的地は 1 件でよいが、サーバー内部では複数候補を許容したほうが堅い。

そのため、内部スキーマは以下を推奨する。

```json
{
  "result": "ok",
  "candidates": [
    {
      "query": "箱根",
      "reason": "山道のドライブ向き"
    }
  ]
}
```

候補が無い場合。

```json
{
  "result": "no_match"
}
```

理由。

- 1 件固定だと Places 解決失敗時に弱い
- LLM 再呼び出し回数を減らせる
- UI 仕様は変えずに内部だけ堅くできる

### 10.1.1 LLM プロンプトに入れる物理制約

LLM には自由に地名を考えさせない。

最低限プロンプトに入れる。

- 現在地の緯度経度
- 片道希望時間
- 有料道路可否
- 日本国内・車移動であること
- ざっくりした到達可能圏の説明

到達可能圏は厳密な円判定ではなく、候補暴走を抑えるための粗い制約でよい。

例。

- 高速可: 高めの平均速度想定
- 高速不可: 低めの平均速度想定

目的は正しさの証明ではなく、明らかに不適切な候補を減らすこと。

### 10.2 LLM モデル名の扱い

モデル名はコードに固定しない。

- `SAKURA_AI_MODEL` を環境変数にする
- ドキュメントには「利用可能モデルはコントロールパネル確認」と書く
- `kimi2.5` 前提で設計しない

これは、さくらの AI Engine 公式 API ドキュメントが「利用可能なモデルはコントロールパネル等をご確認ください」としているため。

### 10.3 Google 側の場所解決

LLM が返す文字列はそのままルーティングに使わない。

必要な処理。

- Places Text Search などで候補を引く
- place ID を得る
- place ID ベースでルートを取る
- 可能なら origin 近傍へ location bias をかける

理由。

- 公式ドキュメントでも place ID 利用が推奨されている
- 曖昧な地名文字列をそのまま使うと誤判定しやすい

Places 側の不成立条件。

- `places[]` が空なら次候補へ
- place ID が取れない候補は捨てる
- 上位 3 件までで打ち切る

### 10.4 ルート取得

Routes API では以下を明示する。

- travel mode: driving
- toll 可否に応じた route modifiers
- 必要な field mask のみ取得
- polyline はまず basic polyline を使う

field mask を使う理由。

- レスポンスを減らせる
- 不要データを返さずに済む
- Worker 内の JSON 処理量を減らせる

basic polyline を優先する理由。

- MVP は地図描画ではなく案内ロジックが中心
- traffic-aware polyline は不要に高機能である
- 公式ドキュメント上、traffic-aware polyline は Routes Preferred の課金対象になる

したがって v1 では以下を避ける。

- traffic-aware polyline
- 不要な代替ルート
- 使わない warning / viewport / 余剰メタデータ

Routes 側の不成立条件。

- `routes[]` が空ならその候補は不採用
- 許容誤差を超える所要時間なら不採用
- route 取得失敗が retry 対象外なら、その候補は打ち切る

### 10.5 Matrix API を MVP で使わない理由

MVP では目的地 1 件を最終的に評価できれば足りるので、まずは `computeRoutes` を使う。

Matrix は以下のときに再検討する。

- 候補地を多数比較したい
- 同時比較で最適候補を選びたい
- ランキング方式を導入したい

## 11. フロントエンドの責務

フロントは案内の中心であり、MVP の成否はここにかかる。

責務は以下。

- 位置情報の取得と監視
- 現在の route step 判定
- 次の案内文生成
- 逸脱検知
- 音声読み上げ
- 画面描画

### 11.1 画面一覧

MVP で必要な画面は 4 つだけ。

- 権限取得画面
- 条件入力画面
- 案内画面
- エラー / リトライ画面

出発地点確認は「住所必須」にしない。

MVP では逆ジオコーディングを必須化せず、以下のどちらかで十分とする。

- 「現在地から出発しますか」という汎用文言
- 参考情報として座標または精度のみ表示

理由。

- 逆ジオコーディングは API 呼び出しを 1 本増やす
- MVP の本質価値ではない

### 11.2 画面に出す情報

案内画面には以下のみ表示する。

- 現在の案内文
- 矢印
- 次の分岐までのおおよその距離
- 現在の状態
- 中止ボタン

MVP では表示しない。

- 地図
- ゴール名
- ゴール住所
- ゴール画像

## 12. 位置情報取得の実装方針

### 12.1 `watchPosition()` を主に使う

現在位置監視は `watchPosition()` を主軸にする。

ただし、ここで注意が必要。

- `watchPosition()` は「位置が変わるたびに呼ばれる」ものであり、固定 3 秒タイマーではない
- 実際の発火間隔は端末・ OS ・ブラウザ・省電力状態に依存する

したがって、実装は以下とする。

- 位置の取得自体は `watchPosition()`
- 案内再評価は「新しい位置が来たとき」に行う
- 必要なら UI 更新の補助として短い interval を置くが、位置取得の基準にはしない

### 12.2 位置情報オプション

MVP の初期値案。

- `enableHighAccuracy: true`
- `timeout: 10000`
- `maximumAge: 3000`

理由。

- 車移動のナビでは精度が重要
- ただしバッテリー負荷は高くなる

この設定は実機検証で見直す。

### 12.3 エラー処理

少なくとも以下を分岐する。

- 権限拒否
- 位置取得不可
- タイムアウト

エラーメッセージは技術用語を出さず、再試行行動を明示する。

### 12.4 Screen Wake Lock

ナビ中は、対応ブラウザで `Screen Wake Lock API` を使う。

実装原則。

- ナビ開始時に `navigator.wakeLock.request("screen")` を試す
- 非対応や拒否時は静かにフォールバックする
- `visibilitychange` 復帰時に再取得を試す
- ナビ終了時に release する

注意点。

- wake lock は visible な document でのみ取得できる
- 非表示化や低電力状態などで解放される場合がある

これは PWA ではなく、MVP に入れてよい小さな UX 改善とみなす

## 13. ナビゲーション状態機械

MVP の状態は以下。

- `idle`
- `requesting_permission`
- `ready_to_start`
- `starting_navigation`
- `navigating`
- `off_route`
- `arrived`
- `error`

状態遷移の原則。

- UI 表示は状態から決定する
- 外部 API 呼び出し中は必ず loading 状態を持つ
- ルート情報がない状態で `navigating` に入らない
- 最終 step 完了かつ終点近傍に入ったときのみ `arrived` に遷移する

## 14. step 判定ロジック

既存メモの方針は活かすが、前提を少し補正する。

### 14.1 step 更新に使う情報

- 現在位置
- 現在 step の polyline
- 次 step の polyline
- 次の曲がり角までの距離
- 進行方向

### 14.2 `heading` の扱い

`coords.heading` は補助情報として使う。

理由。

- 端末や速度次第で信頼性が落ちる
- 停止時や低速時は値が弱い場合がある

そのため、更新判定は以下の優先度にする。

1. 現在位置がどの step の線に近いか
2. 次の分岐点を通過したか
3. `heading` が使える場合のみ補助判定

### 14.3 MVP の案内更新ルール

複雑にしすぎない。

- 800m, 600m, 400m, 200m, 100m, 50m, まもなく
- 上記しきい値をまたいだときだけ案内を更新する
- 同じ文言を連続再生しない

### 14.4 逸脱判定

MVP の逸脱判定は簡易版にする。

- 現在位置が route polyline から一定距離以上離れた状態が連続したら `off_route`
- `off_route` では再計算しない
- 「元のルートに戻ってください」と表示する
- ルートに戻ったら `navigating` に戻る

理由。

- 自動再探索は外部 API コストと仕様複雑性を増やす
- 会話でも後回し項目として整理済み

GPS 揺れ対策として、以下のヒステリシスを入れる。

- 逸脱判定は `max(60m, accuracy * 1.5)` を 2 回連続で超えたら成立
- 復帰判定は `max(30m, accuracy)` 以内に 1 回入ったら成立

これにより、境界付近で `off_route` と `navigating` が振動するのを抑える。

### 14.5 到着判定

MVP の到着判定はシンプルにする。

- 最終 step に入っている
- 最終 step の終端近傍にいる

目的地名は表示しないが、状態としては `arrived` を持つ。

さらに、最終 step 終端から 50m 以内に入った場合は、`off_route` 状態でも `arrived` を優先する。

理由。

- 店舗の駐車場や施設敷地への進入で route 線から少し外れることがある
- `off_route` を優先すると、実質的に到着しているのに終了しない

## 15. 音声案内の扱い

MVP では Web Speech API の `speechSynthesis` を第一候補とする。

ただし、音声案内は必須機能ではない。

- 使えれば使う
- 使えなくても UI は成立させる
- 音声機能の有無を起動時に検知する
- 初回発話は user activation のある操作にひも付ける

理由。

- ブラウザ差異がある
- 音声関連は OS / ブラウザ依存が強い
- MVP では案内ロジックの成立が優先

将来的に安定音声が必要なら、さくら AI Engine の音声 API や別 TTS の検討余地はあるが、v1 では入れない。

### 15.1 音声初期化

Chrome 系では user activation なしの `speechSynthesis.speak()` が失敗する実装がある。

そのため MVP では以下を固定する。

- 「ナビ開始」ボタン押下ハンドラの中で音声初期化を行う
- 初回の短い utterance または実際の初回案内を、その user activation の流れで発火する
- 以後の自動案内は、その初期化成功を前提に行う

この初期化が失敗した場合でも、ナビ自体は継続する。

### 15.2 初期設定

音声案内は `supported` なら初期 ON を推奨する。

ただし、常に UI に mute 切り替えを置く。

## 16. 目的地を隠す設計上の限界

ここは重要。

MVP の「目的地を伝えない」は UX 上の意味に留まる。

完全秘匿にはならない。

理由。

- フロントは案内のために route 情報を保持する
- 技術的に詳しい利用者は通信内容や画面挙動から推測できる
- 終点付近の step 情報や座標は本質的にヒントになる

結論。

- MVP では「通常利用ではゴール名を出さない」までを保証する
- 「悪意ある解析に耐える秘匿」は非目標とする

## 17. データ保持方針

MVP の保持は最小限。

フロントで保持するもの。

- route 全体
- 現在の step index
- 最新位置
- 最新の案内文
- 音声再生済みフラグ

保持媒体。

- MVP ではメモリ保持を基本とする
- `localStorage` / `sessionStorage` への route 永続化は行わない

理由。

- 長距離 route は polyline と step で肥大化しうる
- 復元仕様を入れるとスコープが増える
- リロード後再開は MVP 非対象である

サーバーで恒久保存しないもの。

- ユーザー履歴
- アカウント情報
- 長期の位置情報

MVP ではリロード復元もやらないため、基本はメモリ中心でよい。

## 18. セキュリティとプライバシー

### 18.1 API キー

以下は Worker 側の秘密情報として管理する。

- `SAKURA_AI_API_KEY`
- `SAKURA_AI_MODEL`
- `GOOGLE_MAPS_API_KEY`

クライアントへは渡さない。

### 18.2 クライアントから直接叩かないもの

- さくら AI Engine
- Google Places
- Google Routes

理由。

- API キー露出を避けるため
- リクエスト内容をサーバーで検証するため

### 18.3 リリース前に最低限必要な文書

- プライバシーポリシー
- 利用規約
- Google Maps attribution

位置情報サービスである以上、ここは MVP でも省略しない。

### 18.4 ブラウザとレスポンスヘッダのハードニング

このアプリは route と最新位置をブラウザメモリに保持するため、XSS はそのまま位置情報漏えいに直結する。

したがって、MVP でも以下を必須とする。

- `Content-Security-Policy`
- `frame-ancestors 'none'`
- `base-uri 'none'`
- `object-src 'none'`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- `Permissions-Policy`

CSP は最初から deny-by-default 寄りで設計する。

初期方針。

- `default-src 'self'`
- `script-src 'self'`
- `style-src 'self' 'unsafe-inline'`
- `img-src 'self' data:`
- `connect-src 'self' https://api.ai.sakura.ad.jp https://routes.googleapis.com https://places.googleapis.com`
- `font-src 'self' data:`
- `object-src 'none'`
- `base-uri 'none'`
- `frame-ancestors 'none'`

注意点。

- Vite の dev 環境と本番 CSP は分ける
- 将来 PWA 化するなら `worker-src` / `manifest-src` を追加検討する
- `style-src 'unsafe-inline'` は MVP の現実解であり、CSS-in-JS や inline style を減らせるなら将来さらに締める

Permissions-Policy の初期方針。

- `geolocation=(self)`
- `camera=()`
- `microphone=()`
- `fullscreen=(self)`

実装規約。

- `dangerouslySetInnerHTML` は原則禁止
- ユーザー入力や LLM 出力を HTML として描画しない
- 例外が必要なら明示レビューを必須にする

## 19. 監視・運用・無料枠前提の制約

Cloudflare 無料枠前提では、Worker を重くしないことが必須。

設計原則。

- 数秒ごとの処理はクライアント内で完結
- Worker はナビ開始時のみ主に使う
- 逸脱時も MVP では再ルート計算しない
- field mask で Google 応答を最小化
- LLM 再試行回数は上限を設ける

### 19.1 悪用対策

MVP でも `POST /api/navigation/start` は保護する。

最低限入れるもの。

- body size 制限
- 型検証失敗の即時 reject
- `Origin` / `Content-Type` の検証
- 共有状態ベースの rate limiting

rate limiting は次の順で考える。

1. 公開本番は Cloudflare zone-level rate limiting rule を必須にする
2. staging や zone-level rule が使えない環境では、Cloudflare Workers Rate Limiting binding または Durable Object を使う

やってはいけないこと。

- Worker プロセス内メモリだけでカウンタを持つ簡易 rate limiting を本番防御として扱うこと

理由。

- Cloudflare Workers は stateless で、各 request が別 instance / 別 location で実行されうる
- request 間でメモリ共有されないため、in-memory のみの制御は実効性が低い
- 公開 API の upstream 保護としては不十分
- Workers Rate Limiting binding も公式上 `local to the Cloudflare location` かつ `eventually consistent` である
- したがって binding は staging や補助防御には使えるが、公開本番の唯一の防御としては置かない

注意。

- Cloudflare の Free plan の zone-level rate limiting は counting period が 10 秒単位に制約される
- Workers Rate Limiting binding の `simple.period` も `10` または `60` に制約される
- したがって `5 req/min` のような抽象表現ではなく、`1 req/10s/IP` や `3 req/60s/IP` のように具体値で記述する

### 19.2 ログ方針

本番ログに生の位置情報を残さない。

許容するログ。

- request id
- endpoint
- 処理時間
- status
- upstream の失敗種別

残さないもの。

- 生の lat/lng
- route polyline
- 目的地候補全文

必要なら非本番のみ、粗く丸めた位置情報を一時的に使う。

運用上の実装。

- Worker エラーログを見る
- `1102` CPU 超過や `1027` 無料枠超過を監視する
- `/api/health` を死活確認用に使う
- セキュリティヘッダの実レスポンスを公開 URL で確認する

## 22. オープンな論点

まだ決め切っていない論点。

- 希望時間に対する許容誤差を何分にするか
- 候補地選定で 1 回の LLM 呼び出しで何件返させるか
- 音声案内を初期 ON にするか
- 逸脱判定の距離しきい値を何メートルにするか

ただし、これらは MVP 実装着手のブロッカーではない。

### 22.1 実装着手のための仮置き値

着手時に迷わないため、正式決定までの暫定値を以下とする。

- 希望時間の許容誤差: ±15 分を初期値
- LLM 候補件数: 3 件
- LLM 再試行上限: 2 回
- Places 解決で評価する候補数: 上位 3 件
- 逸脱判定: route から 60m 以上の外れを 2 回連続で検知
- 復帰判定: route から 30m 以内で 1 回検知
- 到着判定: 最終 step 終端から 50m 以内
- `start` API の hard timeout: 8 秒
- rate limiting 初期値: `1 req/10s/IP` を第一候補
- 公開本番の abuse 対策: WAF rule を必須、Workers Rate Limiting binding は staging または補助防御

これらは実機検証で調整する前提の初期値であり、プロダクト仕様として固定した値ではない。

## 23. 採用しない案とその理由

### 23.1 最初から PWA 完全対応

採用しない理由。

- 実装面積が増える
- オフライン戦略やキャッシュ破棄戦略が必要になる
- 今回の最重要価値は「案内ロジックが成立するか」であり、そこから外れる

### 23.2 最初から再ルーティング対応

採用しない理由。

- API コストが増える
- 状態遷移が複雑になる
- 無料枠前提と相性が悪い

### 23.3 クライアントから Google API を直接叩く

採用しない理由。

- API キー管理上の問題が大きい
- リクエスト制御ができない

### 23.4 フロントとバックを別ホスティングに分割する

採用しない理由。

- CORS と環境差分が増える
- MVP に対して運用コストが高い

## 24. v1 の最終判断

MVP は以下の定義で固定する。

- スマホブラウザで動く
- 現在地から出発できる
- 希望時間と有料道路可否を入れられる
- Worker が候補地を選び、Google で検証した route を返す
- フロントが route を持ち、数秒単位で案内を更新する
- 逸脱時は再探索せず、戻るよう表示する
- 目的地名は UI に表示しない
- PWA / オフライン / 復元 / バックグラウンドは後回しにする

この定義から外れる要素は、原則として v1 では入れない。
