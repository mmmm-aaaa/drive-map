# ロジック改修計画

作成日: 2026-04-12

## 1. 目的

現状は、希望片道時間から一律の平均速度で到達可能距離を推定し、その距離感をもとに LLM が目的地候補を出している。  
しかし、都市部と地方では同じ時間でも実際の移動距離が大きく異なるため、短時間帯で特に目的地候補の所要時間ずれが起きやすい。

この計画では、以下を実現する。

- 出発座標に応じて地域ごとの移動距離推定式を切り替える
- 希望時間帯に応じて、地域差の効き方を変える
- 長時間の指定ほど、ルート所要時間の許容幅を広げる
- LLM が有名地に偏らず、時間適合を優先してローカルな具体地名も返せるようにする
- 複数固定座標で、LLM → Places → Routes を実APIで通す一貫テストを追加する

## 2. 今回の結論

以下の方針で改修する。

- 地域判定は外部 API なしで、広域バウンディングボックスによるハードコード判定とする
- 地域区分は 6 つにする
  - `tokyo_core`
  - `tokyo_outer`
  - `kansai_core`
  - `chukyo_core`
  - `regional_city`
  - `rural_default`
- 距離推定は一律線形式ではなく、希望時間帯ごとの段階式に変える
- 希望時間帯は 3 段階にする
  - 1〜3時間
  - 3〜6時間
  - 6時間超
- 短時間では地域差を強く反映し、長時間では全国共通寄りの速度へ寄せる
- 所要時間の許容幅も短時間・中時間・長時間で段階的に広げる
- LLM プロンプトは、有名地優先を抑え、時間適合最優先かつローカルな具体名も許可する内容へ変更する
- 手動スモーク専用の live test を追加し、固定座標で許容時間内に収まることを確認する

## 3. 公開 API の扱い

今回の変更は `POST /api/navigation/start` の公開 API 契約を変えず、内部ロジックのみを改修する。

変更の中心は次の 4 つ。

- 到達可能距離推定
- ルート所要時間の許容判定
- LLM への目的地選定指示
- 実API一貫テスト

## 4. 地域別距離推定ロジック

### 4.1 基本方針

現在は `tollRoadsAllowed` の真偽値だけで平均速度を切り替えている。  
これを、`origin + durationMinutes + tollRoadsAllowed` から推定コンテキストを組み立てる方式へ変更する。

新たに以下の概念を持つ。

- 地域プロファイル
- 時間帯バンド
- 推定直線距離
- Places の location bias 半径

### 4.2 地域判定方法

初回実装では逆ジオコーディングや都道府県データは使わない。  
緯度経度を使い、広域バウンディングボックスで判定する。

#### `tokyo_core`
- lat: `35.55 - 35.82`
- lng: `139.50 - 139.95`

#### `tokyo_outer`
- lat: `35.20 - 36.35`
- lng: `138.85 - 140.40`
- ただし `tokyo_core` は除く

#### `chukyo_core`
- lat: `34.75 - 35.45`
- lng: `136.55 - 137.45`

#### `kansai_core`
- lat: `34.45 - 35.20`
- lng: `134.90 - 136.45`

#### `regional_city`
以下のいずれかに入る場合。

- 札幌: lat `42.95 - 43.20`, lng `141.20 - 141.50`
- 仙台: lat `38.15 - 38.35`, lng `140.75 - 141.05`
- 広島: lat `34.25 - 34.55`, lng `132.30 - 132.60`
- 福岡: lat `33.45 - 33.75`, lng `130.20 - 130.60`

#### `rural_default`
上記のどれにも入らない場合。

### 4.3 判定優先順

重複や包含を避けるため、地域判定の優先順は次で固定する。

1. `tokyo_core`
2. `tokyo_outer`
3. `chukyo_core`
4. `kansai_core`
5. `regional_city`
6. `rural_default`

`kansai_core` と `chukyo_core` は bbox 自体も非重複にし、  
`lng 136.45 - 136.55` はどちらにも入れない。

### 4.4 地域ごとの短距離速度プロファイル

短時間帯で使う初期速度は以下で固定する。

- `tokyo_core`
  - toll: `30 km/h`
  - non-toll: `20 km/h`
- `tokyo_outer`
  - toll: `45 km/h`
  - non-toll: `30 km/h`
- `kansai_core`
  - toll: `40 km/h`
  - non-toll: `25 km/h`
- `chukyo_core`
  - toll: `45 km/h`
  - non-toll: `30 km/h`
- `regional_city`
  - toll: `50 km/h`
  - non-toll: `35 km/h`
- `rural_default`
  - toll: `55 km/h`
  - non-toll: `40 km/h`

### 4.5 時間帯ごとの推定方式

希望時間帯に応じて、地域差の効き方を変える。

#### 60〜180分
- 地域短距離速度をそのまま使う

#### 181〜360分
- 最初の 180 分は地域短距離速度
- 181〜360 分は全国共通の中距離速度

#### 361〜1800分
- 最初の 180 分は地域短距離速度
- 181〜360 分は全国共通の中距離速度
- 361 分以降は全国共通の長距離速度

### 4.6 全国共通の後半速度

#### 中距離速度（181〜360分）
- toll: `65 km/h`
- non-toll: `45 km/h`

#### 長距離速度（361分以上）
- toll: `75 km/h`
- non-toll: `55 km/h`

### 4.7 推定距離の使い方

推定距離は次の 2 箇所で共通利用する。

- LLM プロンプト内の「直線距離の目安」
- Places API の `locationBias.circle.radius`

これにより、プロンプトと Places 検索の制約根拠を一致させる。

### 4.8 Places の半径上限

Google Places API の制約は維持する。

- `locationBias.circle.radius` の上限は `50,000m`
- 長時間希望でも Places バイアス半径は 50km でクランプする

この制約があるため、長時間指定の改善は以下で吸収する。

- LLM プロンプト側の距離制約
- ルート所要時間の許容幅拡張

## 5. 所要時間許容幅の改修

### 5.1 基本方針

現状の許容幅は `max(15分, 希望時間の20%)`、上限 `30分` である。  
これは短時間には有効だが、長時間では狭すぎる。

そのため、時間帯別に許容幅を広げる。

### 5.2 新しい許容幅

#### 60〜180分
- `max(15分, 希望時間の20%)`
- 上限 `30分`

#### 181〜360分
- `max(30分, 希望時間の25%)`
- 上限 `75分`

#### 361〜1800分
- `max(45分, 希望時間の30%)`
- 上限 `180分`

### 5.3 境界値の扱い

`180分 -> 181分` では許容幅が段階的に広がる。  
このジャンプは仕様として許容し、テストで固定する。

### 5.4 定数の扱い

現在の `DURATION_TOLERANCE_MINUTES` は廃止し、  
短時間・中時間・長時間の最小許容分を個別定数へ分ける。

## 6. LLM プロンプトの改修

### 6.1 目的

同じ座標で連続実行したときに、同じ有名地ばかりが候補に出る偏りを抑える。  
ただし、有名地を禁止するのではなく、時間適合を最優先にする。

### 6.2 今回の方針

以下の方向で `destination-selection` プロンプトを修正する。

- 有名かどうかは選定基準にしない
- 希望時間への適合を最優先にする
- 全国的に無名でも、Places で解決しやすい具体地名なら許可する
- 主要観光地は、時間適合が最も良い場合のみ採用する
- 抽象語ではなく、具体的な地名・施設名を返させる

### 6.3 プロンプトに追加する制約

以下の意図を文面に反映する。

- 「全国的に有名かどうかは重視しない」
- 「所要時間に合うなら、ローカルな公園、道の駅、湖、展望台、温泉地、資料館、神社仏閣などでもよい」
- 「有名地ばかりを優先しない」
- 「同じような代表観光地へ寄せず、時間条件に最も合う具体名を 1 件返す」
- 「Places Text Search で解決しやすい具体名にする」
- 「推定直線距離と許容時間帯を優先して判断する」

### 6.4 削除するもの

現状の固定アンカー例は削除する。

- 60分 → 鎌倉 / 川越
- 90分 → 箱根湯本 / 横浜みなとみらい
- 120分 → 箱根 / 日光東照宮
- 180分 → 軽井沢 / 伊豆下田

### 6.5 アンカー削除の代替

アンカー削除で小型モデルの距離感が弱まるリスクがあるため、  
代わりに次を必ずプロンプトへ入れる。

- 地域ラベル
- 推定直線距離
- 許容時間帯
- 近すぎる候補 / 遠すぎる候補を避ける制約
- 再質問時の方向付きフィードバック

### 6.6 維持するもの

以下は維持する。

- JSON 出力契約
  - `{"result":"ok","query":"具体名"}`
  - `{"result":"no_match"}`
- 1件だけ返すこと
- 車移動であること
- 日本国内であること
- 希望片道時間と許容時間帯を明示すること
- 前回候補のフィードバックを再質問時に与えること

## 7. バックエンド実装変更

### 7.1 `backend/src/domain/drive-estimate.ts`

責務を拡張する。

追加または整理する内容:

- 地域判定関数
- 時間帯バンド判定関数
- 地域プロファイル定義
- 段階式の距離積み上げ計算
- 推定コンテキスト生成関数

想定する内部関数:

- `resolveDriveRegionProfile(origin)`
- `resolveDurationBand(durationMinutes)`
- `buildDriveEstimateContext(origin, durationMinutes, tollRoadsAllowed)`
- `estimateReachableDistanceKm(origin, durationMinutes, tollRoadsAllowed)`
- `estimatePlaceBiasRadiusMeters(origin, durationMinutes, tollRoadsAllowed)`

### 7.2 `backend/src/prompts/destination-selection.ts`

次の情報をプロンプトへ渡すようにする。

- 出発座標
- 希望片道時間
- 許容時間帯
- 地域ラベル
- 推定直線距離
- 有料道路可否
- 前回候補フィードバック

固定の有名地例は削除し、地域と時間適合を主軸にした文面へ置き換える。

### 7.3 `backend/src/services/google-places.ts`

`estimatePlaceBiasRadiusMeters` が `origin` を前提にした新しい推定式へ変わるため、呼び出しはそれに追従させる。  
Places API の I/O 契約は変えない。

### 7.4 `backend/src/domain/validate-route-duration.ts`

時間帯別の許容幅ロジックへ置き換える。  
返却形式は現行のまま維持する。

### 7.5 `backend/src/domain/select-destination.ts`

大きなフロー変更は不要。  
現行の以下は維持する。

- Places 未解決なら再質問
- route なしなら再質問
- duration mismatch なら「もっと近い / 遠い候補」で再質問
- リトライ上限と deadline 管理
- `isPlaceholderDestinationQuery` によるプレースホルダー除外

ただし、プロンプト改修により以下の改善を狙う。

- 有名地への偏り軽減
- 所要時間不一致の初回発生率低下
- 再質問の質の改善

## 8. 実装順序

1. `drive-estimate.ts` の地域判定と段階式推定を実装する
2. `validate-route-duration.ts` の 3 段階許容幅を実装する
3. 上記 2 つの unit test を追加・更新する
4. `destination-selection.ts` の prompt を書き換え、既存 prompt test を更新する
5. `google-places.ts` と呼び出し元を `origin` 必須シグネチャへ追従させる
6. `navigation-start` integration test を更新する
7. live 手動スモークテストを追加する

## 9. テスト計画

### 9.1 Unit Test

#### 地域判定
- 各 bbox 内で期待する地域プロファイルが選ばれる
- どの bbox にも入らない座標は `rural_default`
- `kansai_core` と `chukyo_core` の境界付近で誤判定しない
- 判定優先順が意図通りに働く

#### 距離推定
- 同じ 60 分でも `tokyo_core` より `rural_default` の推定距離が長い
- 同じ地域でも toll と non-toll で差が出る
- 10 時間時の地域差が、1 時間時より縮小している
- Places 半径は長時間でも `50,000m` を超えない

#### 所要時間許容幅
- `180 / 181 / 360 / 361` 分で正しいバンドへ切り替わる
- 長時間ほど許容幅が広くなる
- 上限値で正しくクリップされる
- `180 -> 181` の許容幅ジャンプが仕様どおりである

#### プロンプト
- 地域ラベルが含まれる
- 推定直線距離が含まれる
- 有名地を優先しない指示が含まれる
- ローカルな具体地名も許可する指示が含まれる
- 旧来の固定有名地アンカーが含まれない
- JSON 契約文が維持されている

### 9.2 Integration Test

`POST /api/navigation/start` について確認する。

- 地域別推定値がプロンプトに反映される
- 地域別推定値が Places の location bias に反映される
- 長時間リクエストで許容帯が広がる
- `no_match` / `upstream_error` など既存の状態契約が壊れていない

### 9.3 実API一貫テスト

通常の `npm test` には含めず、手動スモーク専用とする。

#### 実行条件
- `RUN_LIVE_NAVIGATION_TESTS=true`
- 実際の LLM API キー
- 実際の Google Maps API キー

#### 固定座標
- `tokyo_core`: 東京駅付近 `35.681236, 139.767125`
- `tokyo_outer`: 八王子付近 `35.655, 139.323`
- `kansai_core`: 大阪駅付近 `34.702485, 135.495951`
- `chukyo_core`: 名古屋駅付近 `35.170915, 136.881537`
- `regional_city`: 福岡市中心部 `33.590355, 130.401716`
- `rural_default`: 長野県松本市付近 `36.238038, 137.971989`

#### テストする希望時間
- 短時間: `90分`
- 中時間: `240分`
- 長時間: `600分`

#### 合格条件
- API 応答が `status: ok`
- LLM が返した候補を Places が解決できる
- Routes が取得できる
- 最終 route 所要時間がその requested duration の許容帯内に入る

#### ログ出力
失敗解析用に以下を記録する。

- region profile
- requested duration
- estimated distance km
- LLM query
- resolved place name
- actual route duration minutes
- allowed window
- diff minutes

## 10. 今回やらないこと

今回は以下をスコープ外とする。

- 実行履歴を保存して同じ候補を除外する仕組み
- 同座標帯の最近候補を永続的に避ける仕組み
- 逆ジオコーディングによる都道府県判定
- 自治体データや GeoJSON による厳密な地域判定
- Places 候補を複数比較してランキングする仕組み
- Matrix API を使った候補大量比較
- feature flag による旧ロジックとの runtime 切り替え

## 11. リスクと対処

### 11.1 bbox 設計の粗さ
- 広域 bbox は行政区分ではない
- 初版は粗い区分で始め、運用ログと live test で調整する

### 11.2 アンカー削除後の LLM 品質
- 固定有名地例を外すと距離感が弱まる可能性がある
- 代わりに地域ラベル、推定直線距離、許容時間帯を強く渡す
- live test で出力品質を必ず確認する

### 11.3 長時間時の Places 制約
- Places の `locationBias` は 50km 上限がある
- 長時間の改善は prompt と duration 許容幅で補う

## 12. 期待する効果

この改修で狙う効果は以下。

- 都市部の短時間指定で、遠すぎる有名地が出にくくなる
- 地方の短時間指定で、近すぎる候補や不自然な候補が減る
- 長時間指定で、短時間向けの厳しすぎる判定に引きずられにくくなる
- 同じ代表観光地への偏りが減り、時間条件により合う具体地名が出やすくなる

## 13. 前提と割り切り

- 地域判定は粗い広域 box であり、厳密な行政区分ではない
- 速度係数は初期値であり、実運用でログを見ながら再調整する前提とする
- Places の 50km 上限があるため、長時間帯の探索精度には限界が残る
- 今回の重複対策はプロンプト強化のみであり、完全な重複防止は保証しない
- live test は通常テストではなく手動スモークとして扱う
